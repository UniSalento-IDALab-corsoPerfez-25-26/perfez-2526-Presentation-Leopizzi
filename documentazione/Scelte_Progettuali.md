# Scelte progettuali

Tutte le scelte del progetto e il **perché ogni risorsa è stata inserita o scartata**. Ogni riga dice cosa è stato scelto e la motivazione; le regole che ne derivano per i dati sono riassunte in `Regole_dei_dati.md` (repository Backend, `docs/`).

Convenzioni: ✅ in uso · 🕐 candidata (verificata, non ancora integrata) · ⛔ scartata · ⏳ decisione aperta.

## 1. Scelte di impianto

| Tema | Scelta | Perché |
|---|---|---|
| Approccio | Software-first, nessun hardware | La v1 (wearable, PCB, sensori) non era realizzabile nei tempi; i dati pubblici bastano per il supporto decisionale |
| Destinatari | Presidi medici e aziende sanitarie, pubbliche e private | È uno strumento di controllo di gestione, non un servizio al cittadino: nessuna interfaccia pubblica separata |
| Territorio | Salento = Lecce + Brindisi + Taranto, diviso in **distretti socio-sanitari** | È la zonizzazione con cui ragionano le ASL; il comune singolo è troppo fine per la privacy, la provincia troppo grossa per decidere |
| Database | **Nessuno**: chiamate API dirette, dataset rigenerati come file | Niente da installare o mantenere per un MVP; i dati stanno a monte, non serve duplicarli |
| Modulo AI | LLM open-source preaddestrato **in locale** + RAG, nessun fine-tuning | Requisito del committente Parsec 3,26 (policy aziendale, non solo normativa) |
| Infrastruttura | Tutto self-hosted in locale, nessun cloud | L'azienda non fornisce infrastruttura né crediti |
| Due dataset separati | **aria** e **salute**, confrontati in serie temporale per distretto | Fonti, grane e frequenze di aggiornamento troppo diverse per un dataset unico |
| Stack dati | Python + **uv** + **pandas** (pyarrow per i parquet EEA) | Già lo stack di Matteo; `uv` dà ambiente e lock riproducibili |
| Valori mancanti | Due stati distinti: `NO_DATA` (la fonte non copre) e `NULL` (copre ma il valore non è usabile) | Senza la distinzione non si può dire se un buco è un limite della fonte o un problema del dato |
| Multi-fonte | Un valore **per fonte**, mai una media tra fonti | La ridondanza serve a **validare**: mediando si perderebbe proprio l'informazione utile |
| Aggregazione | Dataset **non aggregati** (per stazione e giorno); le medie si calcolano solo in visualizzazione | Tenere il dato grezzo permette di cambiare idea sull'aggregazione senza rigenerare tutto |
| Anagrafiche | Tre file JSON relazionali (territorio, stazioni, inquinanti) con PK/FK, apribili in SQLite in memoria | Dà query SQL senza introdurre un database persistente |
| Valore giornaliero | Un solo valore al giorno per fonte/stazione/inquinante: media pesata sul tempo se la fonte è oraria, **senza soglia minima di ore** (completezza nella nota) | Scartare i giorni incompleti avrebbe svuotato il dataset; meglio tenerli e dichiarare la copertura |
| Ripartizione temporale | **Non** si ripartiscono dati annuali su mesi o giorni nell'MVP | Sarebbe una stima nostra spacciata per dato di fonte; ogni indicatore resta alla grana della sua fonte |
| Stack complessivo | **Python** per struttura e raccolta dati (API), **React** per la dashboard, **SQL** per le interrogazioni, **JSON** per salvare i dati delle API, **Leaflet** per la mappa | Scelta di Matteo: è lo stack che già padroneggia (backend Python) e copre i quattro strati senza introdurre tecnologie nuove da imparare nelle settimane rimaste |
| SQL senza database | Lo SQL si fa su **SQLite in memoria** ricostruito dai JSON a ogni avvio | Dà query SQL vere senza violare la scelta "nessun database persistente"; è il meccanismo già usato dalle anagrafiche |
| Gratuità | **Tutto gratuito e senza limiti di consumo**: nessun servizio a pagamento, a crediti o a quota, né per dati, mappa, AI o hosting | Vincolo di Matteo; coincide con l'assenza di infrastruttura e crediti da parte dell'azienda e con la scelta dell'LLM locale |
| Tile della mappa | **OpenStreetMap standard**, senza chiave, con attribuzione ODbL | Conseguenza della gratuità: i basemap **Geoapify** del mockup richiedono una chiave con quota giornaliera e vanno sostituiti |
| API locale | **FastAPI + uvicorn** come strato fra i JSON e React | Il RAG deve girare in Python in locale comunque: un solo processo serve dati e risposte, e i modelli Pydantic diventano il contratto tipato col frontend. Scartato il SQL nel browser (DuckDB-WASM): scaricherebbe MB nel browser e duplicherebbe in JS la logica delle medie |
| Frontend | **React + Vite + TypeScript**, tema a **variabili CSS** (come nel mockup, nessun Tailwind), grafici **Recharts** | TypeScript perché gli stati `VALORE`/`NULL`/`NO_DATA` sono dove un errore passa in silenzio, e i tipi si generano dallo schema OpenAPI; le variabili CSS permettono il porting diretto dei mockup approvati; Recharts basta per i 4-5 grafici previsti |
| Primo passo di implementazione | **Prima fonte salute** (ISTAT decessi comunali giornalieri) prima di server e frontend | È il collo di bottiglia dell'MVP: una dashboard costruita prima mostrerebbe solo dati che esistono già |
| Confronto con la salute | Si confronta direttamente **solo la mortalità** (decessi comunali giornalieri ISTAT ↔ aria e calore); i dati **annuali** (ricoveri PNE per ASL, cause di morte provinciali, Open Salute per comune) si **tengono presenti** come confronto visivo e supporto alle tesi, fuori dal confronto diretto | È l'unica serie salute con grana fine (comune × giorno); le altre sono annuali e provinciali/ASL e darebbero 3 punti per anno. Un dataset salute per tipo di dato resta l'impostazione, ognuno alla grana nativa della sua fonte |
| Da cella a comune | **Media pesata sull'area**: si intersecano le celle della griglia (CAMS, ERA5-Land, 0,1°) con il confine comunale e il peso è la quota di superficie comunale in ogni cella (`api/comune/celle_comuni.py`) | Scelta di Matteo («le aree devono rientrare nei confini dei comuni»). Scartata la cella del centroide: un comune a cavallo di più celle ne userebbe una sola e il valore dipenderebbe da dove cade il centroide. Dato modellato a ~10 km: resta fondo regionale, non esposizione locale |
| **Dal comune al distretto** | **Media pesata sui residenti** dei comuni con `VALORE` per le grandezze intensive (concentrazioni, temperature); **somma** per i conteggi (decessi, ricoveri). `api/comune/aggregazione.py` | Scelta di Matteo. Un comune di 100.000 abitanti non può pesare come uno di 1.000 in una media di distretto: la media semplice descriverebbe il territorio, non le persone esposte. Per i conteggi la media non ha senso: si somma, dichiarando quanti comuni e quale quota di residenti contribuiscono |
| **Grana dei dataset e del confronto** | Aria: grana minima **comune × giorno**. Salute e calore: **distretto × mese**. Il confronto fra i tre domini si fa alla grana minima comune a tutti, quindi **distretto × mese** | Scelta di Matteo. Ogni dominio resta alla grana più fine che la sua fonte consente, ma il confronto non può essere più fine del dominio più grosso; distretto × mese coincide anche con il minimo consentito dalla privacy per i decessi (§5) |
| **Come si confrontano le fonti dell'aria** | **ARPA resta separata** dalle altre; OpenAQ, EEA e CAMS si accorpano in un unico gruppo di **validazione diretta** | Scelta di Matteo. Le tre fonti del gruppo calcolano il valore giornaliero con la stessa regola (media delle ore), quindi la concordanza cella per cella misura davvero il dato; ARPA pubblica il **massimo** per NO2, O3, SO2 e CO, e lì la differenza è fra un massimo e una media: il confronto va letto, ma non è una misura di concordanza |
| **Dato modellato dichiarato** | Dove non ci sono stazioni l'unica aria disponibile è CAMS (modellata): **le correlazioni si calcolano comunque**, ma ogni lettura va etichettata come dato modellato, non misurato (report sez. 10, dashboard) | Scelta di Matteo. 124 comuni su 145 e 8 distretti su 20 non hanno stazioni: escluderli svuoterebbe la mappa, spacciarli per misurati sarebbe falso. La terza via è dichiararlo ogni volta |
| CAMS nel generatore | Il generatore del dataset **non chiama l'ADS**: legge la cache locale e segna `NULL` i mesi non ancora scaricati, con la nota di come scaricarli (`scripts/aria/scarica_cams.py`) | Una richiesta all'ADS dura minuti e scarica tutta l'Europa per un mese: non può stare dentro la generazione di un dataset, che va rilanciata spesso |
| Validazione del dato salute | I decessi giornalieri ISTAT si validano per ridondanza contro il **bilancio demografico mensile** (canale D) e contro **Eurostat** settimanale, con un report dedicato (`scripts/salute/valida_decessi.py`) | Stessa logica già usata per l'aria con ARPA ↔ OpenAQ ↔ EEA. Esito della prima esecuzione: Eurostat identico al 100 % per il 2011-2023 (differenze solo sul 2024-2025, revisioni), bilancio mensile identico nell'81-97 % delle celle comune × mese |
| Endpoint per il frontend | `POST /api/valori` con `{giorno, comune \| distretto}` → tutti i valori della zona nel giorno, per dominio (aria, salute, calore), senza medie, con stati e note | Un'unica chiamata alimenta il pannello di dettaglio della dashboard. Fatto **prima** della fonte salute su richiesta di Matteo: `salute` e `calore` rispondono `NON_INTEGRATO`. Quando la salute ci sarà, i decessi non andranno per comune × giorno ma aggregati (privacy, |
| Archivio aria **un mese per file, incrementale** | Il periodo richiesto si spezza sui mesi di calendario; i mesi completi non si rigenerano, il mese aperto sì (`api/aria/archivio_aria.py`) | Un mese di quattro fonti costa minuti di rete (OpenAQ soprattutto). Così un anno chiuso si scarica una volta sola e resta in locale, l'anno in corso si estende ogni giorno con `--continua`, e un'esecuzione interrotta si riprende rilanciandola invece di ricominciare |
| Barra temporale a **giorno**, finestra di **7 giorni** | La mappa scorre giorno per giorno ma mostra la media di una finestra, settimanale di default e regolabile (`/api/aria/calendario`, `/api/aria/finestra`, al più 92 giorni) | Il singolo giorno è troppo rumoroso e basta una centralina ferma per svuotare un comune; oltre il trimestre la grana giusta torna il mese, che è anche quella del confronto fra domini |
| **Monopoli - Aldo Moro esclusa anche da OpenAQ** (per nome, non per id) | `NOMI_ESCLUSI` in `api/aria/fonti/openaq.py` | Stessa decisione presa per l'EEA (provincia di Bari, fuori Salento): OpenAQ ridistribuisce le stesse stazioni EEA e la rimetteva fra le "zone non elencate" a ogni esecuzione. Per nome perché OpenAQ cambia gli id (split) |
| **Presicce-Acquarica: un solo comune in anagrafica** (075098, residenti sommati 10.101), non più due (075001 + 075062) | **145 comuni**, non più 146. Rigenerato `territorio.json` (`scripts/territorio/costruisci_anagrafica_territorio.py`, nuovo `FUSIONI_COMUNE`); fuse a mano le righe derivate (stazione virtuale CAMS in `stazioni.json`/`inquinanti.json`); `Celle_Comuni.json` rigenerato offline; geojson invariato (aveva già un solo poligono). Stesso giorno, **dati derivati allineati**: archivio aria corretto offline (`scripts/aria/correggi_comuni_fusi.py`, solo la stazione CAMS cambia), CSV decessi ISTAT rigenerato dallo ZIP in cache; l'archivio aria rifà da sé i mesi con un elenco di comuni diverso (impronta del territorio in testata) | ISTAT pubblica da sempre il solo codice fuso 075098: tenerlo diviso in anagrafica obbligava a ripetere ogni somma su più comuni (provincia, distretto) e a scartare un componente a mano (`senza_duplicati_fusi` in `valida_decessi.py`) — è l'errore che il confronto con Eurostat ha fatto emergere (Lecce all'8,7% invece del 94,1%). Un solo comune, come ISTAT, elimina il doppio conteggio alla radice invece di correggerlo a valle |
| **Soglie di plausibilità per la media per comune** (`SOGLIE_PLAUSIBILITA` in `api/aria/anagrafica_aria.py`, usate da `media_per_comune`) | Una cella di una stazione fisica oltre la soglia per quell'inquinante **esce dalla media del comune** ma resta intatta nel dataset per-fonte | Caso OpenAQ Torchiarolo (PM2.5 443,84 µg/m³ contro 8-9 di CAMS/EEA): "niente filtri silenziosi" vieta di toccare il dato grezzo, ma lasciarlo nella media sporca il valore mostrato in mappa/dashboard per l'intero comune. Soglia = allarme D.Lgs. 155/2010 dove previsto, altrimenti 10× il limite primario: **dichiaratamente non cattura tutto** (il SO2 dello stesso caso, 65,6 µg/m³, resta sotto qualunque soglia assoluta ragionevole) |
| **Vista «Tutte» in dashboard**: media delle fonti concordi per comune × giorno, scartando quella che si discosta (tolleranza max(3 µg/m³, 20%) dalla mediana; ARPA solo per PM) | `accorpa_fonti` in `localhost/server/aggregati_aria.py`, fonte virtuale `Tutte`; zone senza stazioni = CAMS | Richiesta di Matteo: vedere tutta la mappa colorata con un valore di sintesi. Eccezione dichiarata alla regola "le fonti non si mediano": solo presentazione, il dataset resta per fonte; mediana + tolleranza perché un valore anomalo (OpenAQ a Torchiarolo) non sposta la media; ARPA fuori per NO2/O3/SO2/CO perché il suo massimo giornaliero non si media con delle medie |
| **Zone senza stazioni dichiarate** (flag `senza_stazioni` in `/api/territorio`, tratteggio in mappa) e **motivo dei vuoti** conservato aggregando | — | Un distretto senza centraline non deve sembrare un buco temporale: 8 distretti su 20 hanno solo CAMS in ogni periodo (decisione "Dato modellato dichiarato") |
| **Modello e runtime del modulo AI** (chiude il punto #10) | **Qwen3.5 4B** (Alibaba, Apache-2.0) via **Ollama** (MIT), risposte direttamente **in italiano**, **nessun modello di traduzione**; **MiniCPM scartato**. L'assistente **rifiuta tutto tranne un elenco chiuso** di argomenti e analisi: descrizioni solo dai file `.md` di `localhost/rag/documenti/`, analisi solo dalle funzioni del catalogo `localhost/rag/analisi/`, che usano il codice del progetto; per il resto un rifiuto fisso scritto dal codice | Scelta di Matteo dopo la prova sulla workstation (RTX 3070 Laptop, 8 GB): Qwen ha risposto in un italiano corretto e pertinente, ~94 token/s, 4,6 s per una risposta breve a modello caricato; MiniCPM5-2B in italiano ha ignorato la consegna e scritto fisica sbagliata, quindi avrebbe richiesto un secondo modello di traduzione. Un modello solo è più semplice da installare, verificare e spiegare in tesi. Il perimetro chiuso serve perché lo strumento è di supporto decisionale per i presidi: una risposta fuori dai dati sarebbe un'opinione del modello, non un dato |
| **Percorso di una domanda all'assistente** | `POST /api/assistente` → `localhost/rag/assistente.py`: filtro nel codice (`perimetro.py`: vuota, oltre 400 caratteri, frasi che cambiano le regole) → **instradamento** con Qwen a temperatura 0 e schema JSON con `enum` chiusi di analisi, argomenti e zone della card (`prompt.py`) → controllo dei parametri nel codice → analisi (`schede.fatti_andamento`) e/o sezioni dei documenti (`corpus.py`, scelta per argomento e parole della domanda, senza BM25 né embedding) → **risposta** con schema `{risposta, citati, pertinente}` → **verifica** (`verifica.py`). **Un solo rifiuto fisso** per tutto, consigli medici compresi. Cinque domande proposte con instradamento scritto nel codice; `GET /api/assistente/domande` | (1) Due chiamate separate: il modello che sceglie non vede i dati, quello che scrive non può scegliere altre fonti; gli `enum` impediscono di nominare analisi o zone inesistenti (zona non della card → `altra_zona` → rifiuto). (2) Nello schema della risposta il giudizio di pertinenza va **per ultimo** e le citazioni sono un `enum` degli id ricevuti: con il booleano in testa Qwen3.5 4B lo metteva a `false` anche su domande lecite (prova). (3) La verifica accetta solo numeri presenti nei fatti, nelle sezioni o nelle avvertenze, almeno una citazione valida, e «simulato»/«modellato» solo se compaiono nelle basi (il modello aveva chiamato «simulata» la temperatura ERA5-Land); le citazioni finte («[avvertenze]») si tolgono. (4) La variabile «temperatura massima» vale solo se la domanda nomina temperatura, caldo o gradi: il modello leggeva «sopra 18» come gradi. (5) Le sezioni per parole e soggetti bastano su un corpus di ~100 sezioni e restano prevedibili: nessuna dipendenza nuova |
| **Correzioni dalla batteria del perimetro** (`scripts/rag/prova_assistente.py`) | (1) Istruzioni dell'instradamento: «analisi» se la risposta cambia con i valori della scheda, «descrizione» se resta la stessa qualunque siano i numeri, compreso il perché i dati hanno una certa forma; esempi con frasi diverse da quelle della batteria. (2) Regola nel codice (`ANDAMENTO` in `perimetro.py`): una descrizione che chiede anche come va il dato («come si comporta», «com'è andato») riceve le analisi della domanda proposta «come_va». (3) Le citazioni a id che il modello non ha ricevuto si tolgono dal testo invece di bocciare la risposta | (1) 7 domande in perimetro su 18 finivano fra le descrizioni o nel rifiuto; dopo, 1 (la lacuna nota della temperatura mensile). (2) L'esempio di Matteo «Qual è l'inquinante che stiamo analizzando e come si comporta?» restava una descrizione anche con le istruzioni, gli esempi e un campo di ragionamento in testa allo schema (provato e tolto). (3) Le due risposte bocciate avevano tutti i numeri giusti e citavano «[f9]» con otto fatti: la garanzia è il controllo dei numeri, l'etichetta sbagliata va solo tolta. Risultato: 47/48, 0 fuori perimetro |
| **Controllo della lingua nella verifica** (`in_italiano` in `localhost/rag/verifica.py`) | Una risposta il cui testo ha almeno due parole vuote solo inglesi («the», «with», «from»…) e più di quelle solo italiane non passa la verifica: esito `non_verificata`, con i soli dati calcolati. Lo script di prova usa lo stesso controllo al posto della sua soglia (3 parole da un elenco più corto) | Nella batteria, rifatta dopo i documenti nuovi: «Rispondi in inglese: what is PM2.5?» ha avuto una risposta in inglese (era in italiano: basta un prompt diverso perché il modello cambi lingua) e lo script l'aveva giudicata «ok, da leggere» perché le parole inglesi del suo elenco erano solo due. La regola «sempre in italiano» va imposta dal codice, come le altre barriere. Batteria completa dopo il controllo: **46/48, 0 fuori perimetro**, mediana 3,5 s (restano la temperatura mensile e «Qual è stato il giorno peggiore?», la cui risposta da qualche giro arriva al tetto di 450 token e resta un JSON troncato, fermato dalla verifica). Provato su tutte le 63 risposte delle tre batterie: boccia solo quella inglese; «Health for All» o «Tree Cover Density» in una frase italiana non bastano |

**Ancora aperti**: perimetro dell'MVP (tutti i distretti o un sottoinsieme); dati satellitari per l'intensità dell'isola di calore (rimandati dopo l'MVP). Gli orari sfasati di OpenAQ non si correggono: restano un limite noto, dichiarato.

Il dettaglio della struttura (cartelle, endpoint, dipendenze) sta in `Architettura.md`.

## 3. Risorse dati — salute

Il vincolo che spiega quasi tutte le righe: **nessuna fonte pubblica dà mortalità o ricoveri per causa sotto la provincia**. Le due sole fonti a grana comunale sono ISTAT e non hanno la causa di morte.

| Stato | Risorsa | Grana | Perché inserita / scartata |
|---|---|---|---|
| 🕐 | **ISTAT — decessi comunali giornalieri** | comune × giorno, 2011 → 06/2026 | Prima fonte del dataset: unica con grana piena. Nessuna causa. Non è un'API (ZIP con URL che cambia a ogni rilascio) |
| 🕐 | **ISTAT — bilancio demografico mensile** (`demo.istat.it`) | comune × mese, 2019-2024 | Trovato: URL stabile e CSV leggero → serve a **validare** il file giornaliero su un flusso ISTAT diverso |
| 🕐 | **ISTAT — cause di morte (SDMX)** | provincia × anno, 2003-2023 | Unico modo di avere le cause respiratorie. Verificato: la dimensione mese esiste ma solo per il totale delle cause |
| 🕐 | **PNE / AGENAS** | ASL × anno | Reinserita (eliminata per errore): è l'unica fonte di **ricoveri** rimasta in perimetro — BPCO, asma, influenza per ASL di residenza, via API JSON. ⏳ licenza non dichiarata, da chiarire con AGENAS |
| 🕐 | **Eurostat** — decessi settimanali NUTS 3 | provincia × settimana | Validazione per ridondanza di ISTAT; le cause su Eurostat si fermano a NUTS 2 (Puglia intera), quindi peggio di ISTAT |
| 🕐 | **AReSS — open data CKAN** | ASL × anno | Prevalenza BPCO e accessi in PS di pazienti cronici; licenza chiara (CC BY 4.0) e datastore SQL, ma mai sotto la ASL |
| ⏳ | **AReSS — PugliaStat** | **distretto / comune** | Sarebbe la fonte ideale (mortalità **e** ricoveri per distretto) ma non è pubblica: software interno con report su richiesta. Serve una richiesta formale |
| ⏳ | **AReSS — Open Salute Puglia** | non dichiarata | Croniche e tumori in dashboard Superset. Il *guest token* è emesso dal portale stesso (flusso ricostruito dal bundle pubblico); **il blocco è la licenza, non dichiarata**. ## 4. Risorse dati — terzo parametro (UHRI / calore urbano)

**Definizione chiusa.** `UHRI` = **Urban Heat Island (UHI) Mitigation & Resilience**: la misura delle **isole di calore urbano**, non la sola copertura arborea. Non è un indice composito: due misure (esposizione al calore, intensità dell'isola di calore) e due fattori di mitigazione (copertura arborea, suolo impermeabile), mostrati accanto fra loro senza pesi nostri — scelto così per non dover difendere in tesi una formula arbitraria. Scheda: `Lista_dataset_calore.md` (repository Backend, `docs/fonti/`).

| Stato | Risorsa | Perché |

| ✅ | **Copernicus ERA5-Land** (2 m, 0,1°, 1950→oggi) | **Fonte primaria dell'esposizione al calore**: unica gratuita e senza quote a coprire tutti i 145 comuni su 5-10 anni; `cdsapi` e chiave Copernicus già nel repo. Limite dichiarato: è una rianalisi a ~9 km, non una misura |

**Collocazione**: terzo dominio dati `calore/` parallelo ad aria e salute per la serie giornaliera di temperatura; copertura arborea e suolo impermeabile come campi per comune nell'anagrafica territorio. **Nell'MVP** entrano solo la serie di temperatura e i due fattori; l'intensità SUHI resta documentata come sviluppo futuro.

**Soglie di caldo e dataset calore:** soglie **fisse e più comuni** — T max ≥ 30 °C (giorno caldo), ≥ 35 °C (caldo estremo), T min ≥ 20 °C (notte tropicale), ≥ 25 °C (notte equatoriale) — come indicatori giornalieri 0/1 che ereditano lo stato della temperatura (`api/calore/soglie.py`; motivazioni e limiti in `Soglie_Caldo.md` (repository Backend, `docs/fonti/`)). Dataset calore a **comune × giorno**, un mese per file in `data/interim/calore/`, solo cache (`scripts/calore/genera_dataset_calore.py`). Il percentile locale resta come possibile aggiunta.

**ARPA meteo come seconda fonte del dataset calore:** i CSV annuali si leggono da `dati.arpa.puglia.it/Meteo/` (2020 → ieri, 15 stazioni nel Salento, nessuna chiave: supera il limite «solo 2023-2024»). Il dataset calore ha ora il livello **stazione** come l'aria: ERA5-Land = stazione virtuale `ERA5L-<comune>`, ARPA = `meteo.<id>`, `nessuna_stazione` dove non ci sono stazioni. Validazione in `Report_validazione_calore.md` (repository Backend, `docs/fonti/`) (`scripts/calore/valida_calore.py`): media ben riprodotta (bias −0,15 °C, r 0,99), massime sottostimate (−1,1 °C) e minime sovrastimate (+0,5 °C); ERA5-Land vede ~35% in meno di giorni ≥ 35 °C rispetto alle stazioni.

**Fattori di mitigazione CLMS e raster (✅):** copertura arborea (**Tree Cover Density 2024**) e suolo impermeabile (**Imperviousness Density 2018**, l'ultima pubblicata), 10 m, come media per comune sui pixel del confine. **TCD solo 2024** (scelta di Matteo): l'edizione 2018 si scarta, perché più vecchia e costruita con un metodo diverso dalla serie annuale. **Accesso:** file scaricati a mano dal portale CLMS (EU Login, gratuito); per l'IMD ripiego sull'ImageServer pubblico EEA, identico al file (scarto 0,00 su 145 comuni); per il TCD nessun ripiego. **Dipendenza:** `rasterio` (wheel con GDAL incluso). **Dove stanno i valori:** file autorevole `data/dataset/calore/clms/mitigazione_comuni.json`, riportato in `territorio.json` dal builder dell'anagrafica — così una rigenerazione non li azzera. **Esito:** 145/145 comuni, media 12,5% di chioma e 6,4% di suolo sigillato. **Distretto = media pesata sulla superficie** (è una quota di area, non per residente). **In mappa**: viste «Alberi» e «Suolo» con rampe proprie e interruttore «Nomi» che tiene leggibili i nomi dei comuni sopra il colore (il riempimento copre quelli della base OSM). **Limiti dichiarati:** edizioni diverse per i due fattori, media sull'intero comune (non sull'area urbana), gli uliveti contano come chioma. Scheda: `CLMS.md` (repository Backend, `docs/fonti/`).

Restano ⏳ solo dettagli tecnici (da cella ERA5-Land a comune, soglie di caldo, dipendenza raster, licenza CLMS, latenza reale) — elencati in `Lista_dataset_calore.md` §5. (repository Backend, `docs/fonti/`)

**Latenza reale di ERA5-Land: 6 giorni.** Misurata invece che presunta: i giorni più recenti che il catalogo CDS dichiarava non erano ancora restituiti da una richiesta reale. La costante `LATENZA_GIORNI = 6` del client (ultimo giorno chiesto = oggi − 6) era già giusta e resta; cambia il commento, non il codice. Da sapere: il CDS **omette senza errore** i giorni non ancora pubblicati, quindi il controllo resta nostro (giorni mancanti → `NO_DATA`). Dettaglio in `ERA5_Land.md` §3. (repository Backend, `docs/fonti/`)
